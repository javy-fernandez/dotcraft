# Remote agent foundation

Issue #141 needs workspace files and .NET tools to live on the same remote machine. `rc-remote` provides a first transport boundary: a standalone `dotcraft-remote-agent` process that reads versioned JSON requests from stdin and writes JSON responses to stdout. The library can launch that agent through `ssh -T` or `wsl.exe --distribution ... --exec ...`, with no terminal allocated. Install or build the matching agent binary on the target machine before connecting. SSH authentication and host keys remain managed by the user's SSH configuration.

Protocol version 1 supports `hello`, `list`, `read`, `write`, `run`, and `cancel`. `read` and `write` carry base64 data, capped at 1 MiB. `run` takes a program, argument array, working directory, environment pairs, and a timeout of at most 120 seconds; stdout and stderr are capped at 1 MiB each. The agent executes as the remote user, so a connection grants that user's filesystem and process rights. Requests have IDs; the server can cancel a running request by ID and drops child processes when their task is cancelled. Responses may arrive out of order. The initial `Client` is sequential; future workspace integration can add a multiplexed client over the same protocol.

This slice does not yet open a remote workspace in DotCraft. The current explorer, editor, file watcher, SDK discovery, Roslyn server, and DAP adapter still use local filesystem paths or local child processes. The next slice should introduce a remote workspace identity and route file listing/read/write/watch through the agent, then route .NET commands and the LSP/DAP stdio streams. A path sent to the agent is always a remote path; it must not be interpreted as a host path or silently mapped through a Windows UNC mount.

The launcher choices follow [Microsoft's WSL command reference](https://learn.microsoft.com/windows/wsl/reference) and [WSL filesystem performance guidance](https://learn.microsoft.com/en-us/windows/wsl/filesystems). No external code or assets were copied.
