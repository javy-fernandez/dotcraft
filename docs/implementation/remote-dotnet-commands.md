# Remote .NET commands

The remote Explorer now runs a configured `dotnet` executable on the remote machine through the agent. The connection form defaults to `dotnet`; enter an absolute executable path if the remote SSH session does not inherit the SDK's `PATH`. After the directory opens, DotCraft runs `dotnet --list-sdks` and shows the installed versions. The toolbar can refresh that list or run `dotnet --info`.

**Build** and **Test** run `dotnet build` and `dotnet test` with the remote folder as the working directory. If a solution or project file is selected in the tree, its absolute remote path is passed as the command target. Otherwise, the .NET CLI resolves the target from the folder. Commands use argument arrays rather than a shell. They run off the UI thread, have a 120-second timeout and a 1 MiB cap for each output stream, and can be cancelled from the Explorer. The client sends a cancellation request with the active command's ID and drains both responses before accepting another command, so later file and SDK requests remain in sync.

The command output is captured when the process exits; it is not streamed live. A long build/test is stopped at 120 seconds, and output beyond the agent's 1 MiB per-stream limit ends the request. No SSH host or WSL distribution was available for a live remote smoke test. Tests use the actual local agent binary with a fake `dotnet` executable for SDK, build, test, and cancellation round trips. A separate local-agent smoke test executed the installed .NET SDK's real `--info` and `--list-sdks` commands. Remote file edits, watches, Roslyn, DAP, terminal, and search remain open under issue #141. This slice builds on PRs #309 and #311; no external code or assets were copied.
